# i18n guardrails

Why each check behind `pnpm guardrails` exists. The rules themselves are in [`AGENTS.md`](../AGENTS.md#i18n).

- `guardrails:translations` runs `i18next-cli extract --ci`: every `t('key', 'Default')` call in `components`, `hooks`,
  `layouts`, `lib` and `pages` must already be in `locales/en/common.json`, so the check passes without modifying locale
  files. Keys are `snake_case`, nested by domain (`about_us.feature_cards.accessibility.title`), always declared with a
  default value. Run `pnpm translations` after adding strings; it also sorts the files.
- `guardrails:i18n-dynamic-keys` rejects keys built at runtime (`t(\`solutions.${x}.title\`)`): the extractor cannot see
  them, so they would never reach the locale files.
- `guardrails:i18n-copy` rejects hardcoded JSX copy in `pages/` and `components/` outside the baseline in
  `scripts/guardrails/baseline.mjs`. User-facing copy goes through `t(...)`; a documented exception is the only way around it.
- `guardrails:translations:parity` compares the key set of every locale with `en` and fails on a missing or stale one.
  It is the only check that catches a dropped key: the extractor sees flat `t()` calls, and the other locale checks only
  inspect keys that exist, so a page reading a whole subtree with `returnObjects` renders a dropped key as an empty
  section rather than falling back to English. The one deliberate exception is `solutions.*.legal.frameworks`, which
  names the statutes of the country the language is read in, so each locale fills it with its own; the check requires
  the section but not its shape.
- `guardrails:translations:non-empty` runs first and rejects empty leaves in every locale: `getMetaByKey` treats empty
  as missing and falls back to English, which hides the gap. Translate the value; a missing key fails the parity check above.
- `guardrails:translations:no-copy` diffs every in-progress locale (`de`, `el`, `eu`, `fr`, `hi`, `it`, `pt`, `pt-br`)
  against `en` and fails on any value identical to the English source. The complete reference locales (`es`, `ca`) tell
  real copy apart from proper nouns, brands and acronyms: a key is only flagged when at least one reference renders it
  differently from English. Values that are intentionally identical to English (brand and product names, proper nouns
  not shared across the references, genuine cross-language cognates) are listed in
  `scripts/guardrails/untranslated-copy-allowlist.json`.

Served locales are defined once in `locales/index.ts`; the blog has its own per-locale files (see
[`content/blog/AGENTS.md`](../content/blog/AGENTS.md)) and is not covered by these checks beyond the `blog.*` UI keys.
